- ✅ **BE-009 statistics** (committed 2026-06-12, NOT pushed). `GET /championships/{id}/statistics` (`[AllowAnonymous]`) → `ChampionshipsService.GetStatisticsAsync` builds `ChampionshipStatisticsDto` from finished matches: TopScorer + TopScorers (players ranked by the goals of the team each controls, via PlayerChampionship — respects "1 player = 1 team, no individual events"), MostWins (team), BiggestWin (largest goal margin), GoalsPerMatch, GoalsConcededPerMatch (best/worst team by avg conceded). **MostAssists and BiggestComeback are intentionally left empty defaults** — no assist events and no in-match progression are stored (only the final score), so they can't be derived. Standings (flat for round_robin + per-group for groups_knockout) were already done earlier. TESTED 14/14 (results compared against locally-computed expectations).
- ✅ **BE-011 refresh-token rotation + multi-session** (committed 2026-06-12, pushed). Separate secret `Jwt:RefreshTokenSecretKey` (placeholder in appsettings, real value in user-secrets); JWT access = **5 min** (`Jwt:ExpirationTimeInMinutes`), refresh = **7 days** (`RefreshExpirationTimeInHours: 168`). New `RefreshToken` entity + `refresh_tokens` table (FK user cascade, index on Token) — one row per active session (multi-session). `TokenManager.GenerateRefreshToken` now signs with the refresh secret, claims sub=user.Id + unique jti(Guid), returns `RefreshTokenResult(Token, ExpiresAt)`; `ValidateRefreshTokenAsync` validates with the refresh secret (`TokenHelpers.GetRefreshTokenValidationParameters`) and returns the userId. `AuthService.IssueSessionAsync` (used by login, register, refresh) generates the pair + persists the refresh row; `RefreshAsync` validates signature/validity, requires the token to be present in the table for that user, then **rotates** (removes the used row, issues a new pair). `POST /api/auth/refresh` (`[AllowAnonymous]`). TESTED 13/13: rotation, used-token→401, chain works, garbage→401, access-token-as-refresh→401 (different secret), two independent sessions. Migration `20260612193013_AddRefreshTokens` applied.
- ✅ **BE-010 RBAC authorization** (committed + pushed 2026-06-12). `UniverseAuthorizer` (scoped, `Services/Authorization/`, uses `IHttpContextAccessor`) resolves the current user from the JWT (`sub`/NameIdentifier) and enforces a minimum `UniverseRole` (enum Moderator=1<Admin=2<Owner=3) per universe; the `UserUniverse` (UserId,UniverseId) PK already guarantees one role per user per universe. Policy (decided by user): **reads are PUBLIC** — GET universes/championships/teams/players/matches/bracket are `[AllowAnonymous]` (no login); creating a universe makes the creator `owner`; **members + content** (championships/teams/players/fixtures generate) require **admin**; **match results** require **moderator**; universe **delete** = owner; granting/changing/removing the **owner** role = owner only. Checks live in the services (each resolves the universeId from the entity and calls `_authorizer.RequireRoleAsync`). `ForbiddenException`→403, `UnauthorizedException`→401. Registered via `AddHttpContextAccessor()` + `AddScoped<UniverseAuthorizer>()`. TESTED end-to-end (21/21): public reads, anon write→401, non-member→403, moderator records results but can't manage content, admin manages content but can't touch owner/delete universe, owner full power. `Dashboard` stays `[Authorize]` (user-scoped). Member LIST (`GET /universes/{id}/members`) is `[Authorize]` (not public).
- 🟢 BE-008 fixture generation — all three formats DONE. Design in `docs/be-008-fixtures.md` (see [[be-008-fixtures-doc]]). Done: engine infra (`FixturesService`, `IFixtureGenerator`), `POST /championships/{id}/generate`, pool lock, the **round_robin** generator (circle method, bye, optional double round), the **knockout** generator (single AND double elimination), and **groups_knockout**.
  - Knockout details (as of 2026-06-12, uncommitted on `main`) — **FULL pre-generated bracket** (not round-by-round; the user wants to enter results of any phase without finishing the previous round first). `KnockoutEngine.BuildBracket(teamIds, thirdPlace)` builds EVERY round/match up front: round 1 = real play-in matches (random draw; bye = next-power-of-two surplus seeded straight into round 2, interleaved so a bye meets a winner), later matches start with **empty team slots** linked via `Match.HomeSourceMatch`/`AwaySourceMatch` (+ `Home/AwaySourceOutcome` = "winner"/"loser"). Third-place round (`Round.Bracket="third_place"`) appended at generate time when `thirdPlace` is set and both semifinals are real matches (fed by the 2 SF losers). `KnockoutFixtureGenerator` just wraps it in a `knockout` phase. Advancement = **slot propagation**, not round creation: `FixturesService.PropagateKnockoutResultAsync(matchId)` fills (or clears, on a reverted result) the team slots of any match whose `Home/AwaySourceMatchId == matchId`, skipping dependents that already have a result. So a match becomes playable as soon as its own two feeders are decided, independent of the rest of the round.
    - Data-model change for this: `Match.HomeTeamId`/`AwayTeamId` are now **nullable** (empty slot) + new `HomeSourceMatchId`/`AwaySourceMatchId` (self-FK, `OnDelete SetNull`) + `Home/AwaySourceOutcome` (string?). Migration **`20260612002415_AddKnockoutBracketLinks`** created AND applied to the DB. Many read projections were made null-safe (MatchesService.GetById, ChampionshipsService.BuildRounds + BuildStandings guard, DashboardService.ApplySide takes int?, RecentResults uses `HomeTeam!.Name`); `MatchSummaryDto.HomeTeam/AwayTeam` are now `string?` (null = "a definir").
    - `MatchesService`: rejects setting a match to ongoing/finished while a team slot is null ("Os times desta partida ainda não foram definidos"); persists penalties only when a finished match is drawn; calls `PropagateKnockoutResultAsync` on every update. `UpdateMatchResultDto` has `Home/AwayPenalties` (int?); penalties surfaced in `MatchSummaryDto` + both projections. Build green (2 pre-existing warnings only).
    - **TESTED 2026-06-12 end-to-end via HTTP** (register → universe → 6 teams → 6 players → knockout champ + thirdPlace → pool → enroll(3 manual)+draw(3) → generate → results entered out of order): 58/58 assertions passed. Confirmed: full bracket pre-generated (Quartas/Semi/Final/3º), byes seeded into Semis, a Semi became playable after only ONE quarter (not waiting for the round), penalties decide a drawn Semi, winner→next slot and loser→third-place propagated, 400s for playing an undecided slot and for a drawn knockout without penalties, champion + 6-row standings at the end.

  - **Double elimination** (committed 2026-06-12) — `KnockoutEngine.BuildDoubleEliminationBracket(teamIds)`, routed by `KnockoutFixtureGenerator` when `config.Elimination == "double"`. Builds the WHOLE bracket up front with the same source-link mechanism: winners bracket (`Round.Bracket="upper"`), losers bracket (`"lower"`, canonical minor/major interleave — LB1 pairs WB1 losers, then for each WB round r≥2 a *major* round mixes LB survivors with that round's WB losers followed by a *minor* round), and a single **grand final** (`"grand_final"` = WB winner vs LB winner; MVP, **no bracket reset**). **No code change to propagation** — the existing winner/loser slot propagation already handles it. **Requires a power-of-two team count** (no byes in DE yet) → otherwise 400 "A dupla eliminação requer um número de times igual a uma potência de 2". `third_place` is ignored for DE. TESTED end-to-end via HTTP with 8 teams (25/25 assertions): 3 WB + 4 LB + 1 GF rounds, 14 matches (2N−2), WB1 losers drop to LB1, full play-through to a champion; DB confirmed the exact canonical linkage; 6-team DE correctly rejected with 400.

  - **groups_knockout** (committed 2026-06-12) — `GroupsKnockoutFixtureGenerator` builds TWO phases: a `groups` phase (Type="groups", Order=1) with `Group`+`GroupTeam` rows and a per-group round robin merged matchday-by-matchday into shared rounds (each group-stage `Match` has `GroupId` set), and a `knockout` phase (Order=2) whose first round is **seeded from group standings**, not match results. New seeding mechanism: `Match.HomeSourceGroupId`/`AwaySourceGroupId` (FK Group, SetNull) + `Home/AwaySourceGroupRank` (1-based) + `Home/AwaySourceGroup` navs — migration `20260612152835_AddGroupSeedLinks` (applied). The knockout advancement reuses `KnockoutEngine.BuildAdvancementFromMatches` (extracted from `BuildBracket`; round-robin's `BuildMatchdays` was likewise extracted for reuse). Propagation: `FixturesService.PropagateResultAsync` (renamed from PropagateKnockoutResultAsync) now routes by phase type — knockout → winner/loser slot fill (`PropagateKnockoutSlotsAsync`); groups → `PropagateGroupQualifiersAsync` which, once **all** matches of a group are finished, ranks it (`RankGroup`: points→GD→GF→wins→teamId, points from win_points/draw_points rules default 3/1) and fills the knockout slots seeded from it (clears them if a group result is reverted). **MVP scope:** equal groups, `groups_count` a power of two, `qualifiers_per_group == 2`, `bracket_seeding == cross_adjacent` (1A×2B, 1B×2A, …) — other configs return 400. TESTED end-to-end (21/21): 2 groups of 4, finishing ONLY group A filled 2 of 4 semifinal slots with group-A qualifiers (semis not playable until group B also finished), full play-through to a champion; DB confirmed the exact cross_adjacent linkage; 4 negative configs correctly rejected with 400.

  - **Bracket read endpoint + per-group standings** (committed 2026-06-12). `GET /championships/{id}/bracket` → `ChampionshipsService.GetBracketAsync` returns the knockout phase as `BracketDto` (rounds ordered by Number then Bracket; each `BracketMatchDto` = id, position, home/away `BracketTeamDto?` with goals, `WinnerId` via new non-throwing `KnockoutEngine.WinnerOrNull`, status, and `NextMatchId` = the match this one's WINNER feeds — DE loser-drop links are NOT in NextMatchId). `BracketRoundDto.Bracket` added (upper/lower/grand_final/third_place) so the frontend can group. 400 if the championship has no knockout phase. Per-group standings: `ChampionshipDetailDto.Groups` (`List<GroupStandingsDto>`) added; `GetByIdAsync` now sets `Standings` only for round_robin, `Groups` only for groups_knockout (knockout gets neither). `BuildStandings` refactored to share `ComputeTable(roster, matches, win, draw)`; `BuildGroupStandings` builds one table per group from that group's matches. TESTED (19/19): bracket for single/double elim + groups_knockout, connectors, winnerId, empty slots; per-group tables (played/points/positions); round_robin still flat + /bracket→400.
